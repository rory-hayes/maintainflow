# Email verification — contract and acceptance

Contract begun 14 September 2026; local checkpoint refreshed 19 September 2026. This increment adds verification for newly registered accounts and optional verification for existing accounts. Implementation and local acceptance are complete for the tested flow with controlled senders. No hosted migration, actual sender configuration or inbox delivery is established by this document. Password recovery's dated evidence remains in [ACCOUNT-RECOVERY.md](ACCOUNT-RECOVERY.md). The original 47 capability IDs and acceptance criteria remain unchanged.

## Account access and public responses

`FOLIO_REQUIRE_EMAIL_VERIFICATION` accepts only `true` or `false` when present. Its default is true in production and false in local/test environments. Malformed settings stop startup. An explicit development/private-preview bypass does not mark any address verified. The policy is stored on each new account: disabling the flag or sender later does not unlock an account created with verification required.

Migration 029 gives existing users `email_verification_required=false` and `email_verified_at=null`. Existing users retain workspace access, sessions, memberships, documents and API keys. The nullable timestamp records actual subsequent confirmation; it is never backfilled from registration or password history.

| Surface | Behavior |
| --- | --- |
| Required signup | Valid fields and any required preview invite enter an encrypted registration queue. New and existing addresses receive the same generic 202 response. Public admission performs no account lookup and returns no session cookie or workspace identity. |
| Queued registration | For a new address, the worker atomically creates a required, unverified user, workspace, owner membership, verification token and mail. A duplicate never updates the existing password, profile or memberships. Expired envelopes are discarded without provisioning an account. |
| Pending sign-in | Correct credentials for an unverified required account still receive `Email or password is incorrect` with HTTP 401. Session creation rechecks the requirement under the user lock. |
| Workspace access | Central session and API-key authentication reject required, unverified users before returning an actor, applying scopes or recording API-key use. There are no account-only sessions bypassing workspace authorization. |
| Existing-account verification | Personal verification controls are available to existing unrestricted users, including viewers, without changing workspace settings. |
| Configuration | `/api/config.emailVerification` returns `{available,requiredForSignup}`. Workspace settings report actual sender capabilities. Availability does not prove inbox delivery. |

When verification is required but mail admission is unavailable, signup returns a safe 503 before creating a user or request. There is no fallback to an unrestricted account. When verification is optional, the existing immediate 201 registration remains available, with truthful optional-verification guidance.

## Requests and confirmation

`POST /api/auth/email-verification/request` accepts `{email}`. Known and unknown valid addresses receive the same 202: **If this email belongs to an account awaiting verification, a verification link will be sent shortly.** The public transaction records an encrypted address envelope without resolving account existence. The worker later sends only for an existing, unverified account. A request does not change credentials or memberships, create an account or sign anyone in. Recipient, origin and subject come from stored account/configuration values.

Registration and verification requests each have their own atomic 5,000-pending-request cap, HMAC-address 60-second cooldown and five grants per one-hour window. IP limits also apply. While capacity is available, address suppression retains generic acceptance. Capacity failures are account-independent. Expiry is 24 hours from original request admission using database time; queue delay and retries do not restart it.

The link is `/verify-email/confirm#token=…`, built only from trusted `APP_ORIGIN`. Before routing, the page captures the fragment into memory and removes it from history. Tokens never enter browser storage, rendered values, API URLs or referrers. Reload requires reopening the original email link. GET and link previews never consume tokens. Application and packaged static routes set no-referrer and private/no-store headers.

`POST /api/auth/email-verification/complete` requires **both `{token,password}`**. A click alone cannot activate an account someone else registered using an address they do not control. Password proof uses the existing sign-in range of 1–128 characters, without applying password-creation guidance. Confirmation works signed out or on another device and never trusts the current cookie to select or switch an account.

Wrong passwords and invalid, expired, used or stale links share HTTP 400 and **We could not verify your email. Check your password, or request a new verification link.** A wrong-password response preserves the link in page memory for correction. Success records the actual verification time, revokes that account's browser sessions, invalidates its verification and password-reset tokens/mail, and writes a bounded security event atomically. It does not automatically sign in. Other accounts/sessions are unaffected. API keys remain independently revocable; required pending users cannot use them before verification.

Password reset or Settings password change never implicitly verifies email. Either invalidates outstanding verification tokens/mail. Workers discard verification requests predating a password change and recovery requests predating successful verification, using actual timestamps without inventing password-change events.

## Concurrency, delivery and storage

Tokens contain 32 random bytes. Storage contains a token digest, purpose, current-email HMAC, credential digest and expiry. Password proof runs outside a transaction and is fenced against the same hash after acquiring the user lock. Consumption rechecks email, credential, purpose, expiry and unverified state under that lock. Concurrent consumption has one winner; audit failure rolls back the whole change.

Queue resolution locks request then user. Confirmation and credential changes do not delete queued request rows under a user lock; timestamp cutoffs avoid a reverse lock order. Registration provisions within a savepoint and checks the original deadline after issuance; expiry rolls back newly created account records before discarding the request.

Verification uses the existing dedicated, disabled-by-default Resend account-email sender. The fixed subject is **Verify your Folio email**. Outbox kind and subject must match before transport. Payloads use AES-GCM encryption. Provider calls are awaited, bounded and outside database locks. Finite retries use stable idempotency keys, expiry and lease fencing. Diagnostics contain fixed codes, never mail contents or credentials.

One mail unit admits at most one request, rotating across registration, verification resend and password recovery, then claims one outgoing email. Busy queues receive progress without creating three outgoing messages per message sent. The existing independent local/hosted email lane remains separate from extraction. Bounded expired-payload cleanup runs even with sending disabled.

A resolver failure rolls back only that request's transaction and leaves it queued for retry. Each queue is attempted at most once per unit, so a retained failure cannot prevent a peer request or an already-ready outgoing email from progressing. If no request progresses and no email can be claimed, any resolver failure produces only the fixed error `Account email request processing failed.` for the worker's existing error handling and idle backoff. Raw database errors, recipients and tokens are not attached to that error. Successful peer admission counts as progress even when an unknown address correctly produces no email. Deadline and cancellation checks still stop work when its budget is exhausted.

Migration [029](../migrations/029_email_verification.sql) adds backend-only forced-RLS tables: `account_registration_requests`, `account_registration_limits`, `email_verification_requests`, `email_verification_limits` and `email_verification_tokens`. The wrapper restores PUBLIC/tenant revocations after broad grants. The shared outbox adds a separate verification-token reference, preserving reset-token constraints and terminal rows whose token references were removed.
