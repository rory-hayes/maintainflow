# Architecture

Decision record, processing contract updated 13 September 2026. Internal project: Parseur. Original application identity: Folio. Earlier local/deployment decisions retain their dated scope; [current hosted status](HOSTED-PREVIEW-STATUS-2026-09-13.md) records the later preview and provider evidence.

## Runtime

React, TypeScript, Vite and React Router compose feature-owned screens. Shared design tokens apply to both the public site and application. Fastify provides a same-origin typed API. PostgreSQL 17 stores accounts, memberships, parser configurations, immutable schema versions, document metadata, jobs, extraction runs, corrections, approvals, exports, integrations, usage and audit records. The local W03 source adds durable field-suggestion requests. A separate worker claims extraction and suggestion jobs transactionally using SKIP LOCKED and leases; it runs independently from the HTTP process. The locally implemented hosted worker coordinates extraction and suggestion rounds, rechecking both after either makes progress so temporary FIFO/capacity blocking does not strand the other queue until another invocation. Both use a 110-second invocation-budget reserve. This scheduler change is not deployed.

The initial 7 September installation used the installed PostgreSQL binary, real password authentication in the application, and a private filesystem object-storage adapter. The later invite-only hosted preview uses an isolated Supabase schema and private object storage; application authentication remains local. Hosted runtime, provider and migration acceptance are recorded separately in [current hosted status](HOSTED-PREVIEW-STATUS-2026-09-13.md).

## Local isolation

The development database and private files live under ignored `.local/` inside this project. The PostgreSQL Unix socket is inside a user-private directory, with TCP disabled. A restricted application database role uses forced row-level policies with transaction-local workspace context. Worker and migration access is separate. The application binds to loopback by default. Every resource lookup also carries the authenticated workspace identifier. Passwords are scrypt hashes; session and API bearer tokens are stored as hashes. Cookies are HTTP-only, same-site and secure in production. Mutations validate the Origin header for browser sessions. Scoped API keys are revocable.

## Processing contract

Ordinary intake validates filename, inspected format, byte and page limits before accepting a document. Each upload receives a SHA-256 digest; ordinary content duplicates are scoped to a parser. PDF splitting uses the separate request identity and atomic batch contract below. Migration 022 adds nullable `allowed_formats`, exposed as `allowedFormats` in parser create/update responses and Settings. `null` preserves legacy acceptance of all supported formats; a selected nonempty set governs future intake, including multipart/API uploads, email items and direct-upload finalization. Existing documents and their reprocessing are unchanged. Accepted original bytes remain private, and a queue transaction creates the document and pinned extraction request.

Recognizable binary formats, full HTML documents and explicit MIME email header structures take precedence over filename classification and cannot be downgraded to plain text by renaming. CSV, plain text, HTML fragments and non-MIME email can overlap, so ambiguous text remains extension-informed. From/Date labels alone do not convert ordinary receipt text into an email. This is bounded format recognition, not detection of every possible file type.

A format-policy or typed source-validation rejection creates no document, extraction job or usage charge. Migration 023 adds a finite source-reason catalogue to the existing rejection receipt shape, with no fabricated format for an undecodable source. Only validated `SourceValidationError` reasons cross the strict decoder protocol as permanent failures; numeric HTTP status, library message/name lookalikes, unknown faults, missing dependencies, timeouts, crashes and invalid decoder responses do not establish a permanent source decision. Decoder output-limit failures remain operational failures. Source-validation rejection occurs before original storage; format-policy rejection uses the existing temporary-original cleanup workflow.

When an idempotency key is present, the transaction commits a rejection receipt bound to that key, SHA-256 digest and parser together with a bounded `document.rejected` audit. Active-parser and tenant checks, existing accepted/rejected receipts and content duplicates are resolved under the workspace lock before decoding, then rechecked before a new decision commits. Exact replay retains its original outcome without decoding again; different bytes/parser under an existing key return a conflict, and deleted accepted receipts remain 410 tombstones. A new attempt/key is required for repaired content or a changed policy. Receipt and audit failures roll back together. Receipts and audits retain finite reasons and identifiers without filenames, email bodies, subjects, credentials or original contents.

Resend preserves sender allowlisting and skips handled body/attachment receipts on retry. It continues after a permanent rejection only when the stored receipt matches the key, bytes, parser and typed reason. An ordinary transient item failure is retained while later items are attempted; successful items keep their checkpoints and the worker retries unfinished items within its existing five-attempt budget. A route with an unresolved item does not update its received timestamp. A work-budget yield stops the invocation; if a real failure occurred earlier, that failure still consumes an attempt. Reaching the 25 MiB aggregate cap stops further downloads/intake immediately, including when downloaded bytes exceed provider metadata. Provider retrieval failures and metadata/download byte-limit failures are not converted into permanent source receipts because complete validated source bytes are unavailable. HTML-only email is represented as stable EML bytes and decoded inside central intake.

For ordinary uploads, only a proven byte mismatch or committed format/source rejection permanently fails a direct-upload reservation and requires a new upload. Untyped decoder or storage errors leave the reservation pending so finalization can be retried; numeric status alone is insufficient. Its signed staging object still counts toward the recent-upload/storage cap until the existing cleanup window closes; cleanup is deferred until after capability expiry, not immediate deletion while that capability may remain valid. Office metadata checks bound entry count and declared expansion, not streaming inflation or native memory; the subprocess limits below remain a separate boundary.

## PDF splitting

The current C10 source implements an explicit split of a **newly uploaded PDF**, using every N pages or one-based, inclusive custom ranges. Ranges stay ordered and nonoverlapping; omissions and a single output are valid. Normal upload remains unsplit. Creation requires an active parser with completed field setup and PDF allowed by its current source policy. Initial sample setup is excluded. Migration [027](../migrations/027_pdf_splitting.sql) and this workflow are **local only**; hosted migration/runtime acceptance remains separate. Keyword/AI splitting, TIFF, existing-document resplitting/reversal and archive expansion remain outside this implementation.

The [isolated splitter](../server/core/pdf-split-engine.ts) validates the source with PDF.js, copies the selected pages into independent PDFs with pdf-lib, and decodes each child again. It retains the original bytes unchanged and rebases child text evidence to page 1. Shared planning and parent-process response validation check exact ranges, page counts, canonical Base64, PDF signatures, ordered child pages and aggregate sizes. Limits are 10 MiB input, 30 source pages, 20 children, 10 MiB per child, 20 MiB combined child PDFs, and 2 MiB text for the source and independently for all children. Splitting shares the ordinary decoder's two-process capacity, 30-second kill deadline and credential-free environment. Compiled JavaScript retains a 192 MiB V8 heap; TypeScript/TSX source execution receives 256 MiB for its trusted loader/compiler overhead on Node 24. Its IPC response allowance is 42 MiB for PDFs and text; ordinary responses remain limited to 4 MiB. These are bounded page-copy and text-processing guarantees, not a claim of complete PDF-feature or visual fidelity. The existing OS/native-memory isolation limits still apply.

[Batch intake](../server/core/pdf-split-intake.ts) writes private source/child objects under durable intents, then commits one accepted receipt, all child manifests/documents, pinned extraction jobs, selected-page usage and bounded audits in one transaction. Workspace advisory and parser locks serialize acceptance; direct reservations and sorted intents are checked before commit. Current parser readiness, source policy, schema, job configuration and quota are rechecked after storage writes. Any transactional failure leaves no partial documents, jobs or page charges. Only selected child pages consume upload credits; the retained original is not a separate extraction document. Jobs use the ordinary extraction/review path, with no automatic approval or export.

`pdf_splits` binds a workspace-unique request UUID to the parser, source SHA-256 and canonical split specification. Exact accepted/rejected replay is resolved before decoding or new writes; changed binding returns 409. An explicitly new request creates a new charged batch even for identical source bytes. Validly bound attempts persist finite typed source, split-validation and format-policy rejections without filenames, source contents, documents, jobs or usage. Unknown faults, storage failures, crashes, timeouts and malformed IPC remain retryable. `pdf_split_children` keeps immutable ordered document/job identities and original page ranges after document deletion. Forced tenant RLS and composite foreign keys join the batch, manifest, parser and live document. Ordinary byte deduplication applies only where `pdf_split_id IS NULL`; identical children still have separate batch/index identities and their actual digests.

Temporary-storage accounting allows two active split attempts per workspace and two concurrent writes per attempt. A 120-second acceptance fence includes elapsed direct-finalizer work; intents have renewable five-minute leases. Split reservations and direct staging share a 250 MiB temporary-byte allowance. Failed or uncertain writes release the active-attempt slot while retaining their byte reservations until removal is confirmed; delayed/failed deletion cannot silently free this allowance. Unconfirmed late writes receive a five-minute deletion delay. Cleanup checks committed document **and batch-source** references even after an uncertain COMMIT acknowledgement. Reconciliation preserves retained sources and queued split-byte reservations. Signed staging is never adopted as an accepted original and remains subject to capability-expiry cleanup. Fresh staging for the same bound split does not add a second provisional page reservation, but every physical staging object still counts toward active/object/byte caps. Final acceptance always checks actual selected pages.

[Split routes](../server/core/pdf-split-routes.ts) require owner/admin/editor access and `documents:write` for multipart creation and whole-batch deletion; the direct reserve/finalize path uses the same write boundary. Browser mutations use the existing origin guard. Multipart accepts exactly one `file`, a UUID `requestId` and JSON `options`, returning HTTP 202 with the batch receipt. Direct reservation accepts `pdfSplit: {requestId, options}` and persists it; finalization dispatches those stored values and commits its completed receipt under the same owner/lease fence as batch acceptance. `GET /api/parsers/:id/pdf-splits/requests/:requestId` requires `documents:read`, supports archived-parser recovery, and returns 404 when no receipt exists. Public receipts include ordered IDs, ranges, page counts and availability, excluding storage keys, source hashes, extracted contents and lease owners. The browser saves only scoped request/spec/digest and optional staging identity in session storage, checks the receipt after reload, and verifies the same file digest before retry. Only an explicit start-new action changes request identity.

Document detail includes split lineage. The existing `/original` remains the child PDF; `/bundle-original` and `/bundle-original-url` authorize the full source through a live owned child using `documents:read`. Review keeps child-local evidence navigation and shows original page numbers. **Omitted pages and pages from deleted children remain in the full original while any child survives.** Single-child deletion clears its stored filename but preserves the replay manifest. Last-child deletion clears the source filename/key and queues removal; whole-batch deletion atomically removes retained documents and their derived database records, then reports durable pending/failed/complete storage status, including on replay. A queued deletion is not confirmation of physical removal. Deleted children return `available: false` without recreation or new credits.

The local PDF preview renders with strict PDF.js errors, a 16-million-pixel declared-image limit, a bounded canvas resize threshold, and a final canvas capped at 2048 pixels per edge and about four million pixels. These do not cap all native/browser memory or prove raster fidelity. Readiness is tied to completed rendering of the current file/page; failed partial renders are cleared and cannot mark the split ready. Review retains original-file download when preview fails.

PDF.js 6.3.289 can otherwise report a successful empty render after its worker rejects an operator stream. A [narrow Vite transform](../scripts/pdfjs-render-errors.ts) rejects the pending operator-list and render promises, cancels active renders with the original error, and evicts the failed intent so retry cannot reuse partial operators. It applies to the browser module in both development and production; dependency prebundling is disabled for that module. The transform requires the exact reviewed version and error branch and fails when either changes. The dependency files and server decoder are unchanged. [Regression coverage](../tests/pdfjs-render-errors.test.ts) executes the transformed installed module with real PDFs, including oversized-image rejection, concurrent callers, retry and valid raster output; this does not establish complete PDF raster fidelity.

## Field suggestion contract

Manual field suggestions use an explicit request from an already uploaded document belonging to the same parser. Opt-in first-document setup uses the same durable suggestion provider under the additional contract below. `POST /api/parsers/:id/schema-suggestions` accepts `documentId`, the current `baseSchemaId` and a UUID `requestId`, returning HTTP 202 with the durable request. Creation requires an owner/admin/editor, `parsers:write` plus `documents:read`, and the browser origin guard. The list and individual-request GET endpoints require `parsers:read` plus `documents:read`; the list returns the latest ten requests, provider availability and limits. Cross-workspace access is denied. Exact request replay returns the original row before checking quotas/provider availability; reuse for another parser, document or base schema returns 409.

Migration 024 adds `schema_suggestions` with forced tenant RLS, composite workspace/parent foreign keys, pinned source SHA-256 and parser configuration, and queued/processing/ready/failed states. A workspace lock enforces **10 new requests per rolling 24 hours** and **three pending requests**. The daily count uses minimal request audits and survives source deletion. Suggestion and extraction claims share the plan's `maxConcurrent` allowance under a workspace row lock, with a fresh combined count and precedence for older eligible work across both queues. Suggestions have at most three attempts and 120-second leases. A 90-second attempt deadline covers metadata, original storage read, checksum validation, provider work and output validation; cancellation checks prevent a delayed read from starting a late provider call. Completion/failure writes require the current processing lease. Scheduled retention excludes sources with queued/processing extraction or suggestion work and rechecks eligibility under the document lock. Explicit source deletion cascades suggestions and prevents late results from recreating them. Audits contain bounded action/identity metadata, not source contents or provider diagnostics.

The adapter uses pinned `gpt-5.4-mini-2026-03-17` and `folio-openai-schema-suggestion-v1`. PDFs and PNG/JPEG include original bytes plus native page text; other accepted formats use decoded native pages. Limits are **10 MiB source**, **30 pages**, **512 KiB native text**, **1 MiB response**, **16,000 output tokens**, and an **80-second adapter deadline**, including response-body reading. The strict recursive Structured Output and runtime validation permit at most **60 total fields**, **four levels** and **30 children per group**, without silent truncation. The adapter proposes field/table metadata only; it rejects required flags, defaults, enums, transforms and anchors inferred from a single sample. Requests treat documents as untrusted data, expose no tools and set `store: false`. Only the application-owned `SchemaSuggestionProviderError` can supply a stored safe failure message; unknown dependency/transport failures stay generic and retryable. [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) supports recursive references; the [model reference](https://developers.openai.com/api/docs/models/gpt-5.4-mini) records supported inputs and token prices.

The Fields UI lets the user select a sample, request, review, use, edit or discard a draft. Using a draft confirms replacement of unsaved edits, including invalid widget input that has not yet committed to schema fields. For these manual drafts, an explicit save to `POST /api/parsers/:id/schema` creates an immutable schema version. The UI supplies `baseSchemaId` for every save; a changed active schema returns 409. Applying `suggestionId` also requires a ready, unapplied suggestion from the same parser/workspace/base and an active parser. The new version, `applied_schema_id` and audit commit together. Existing manual API clients may omit the optional base version. Manual suggestions never automatically modify saved fields, extraction runs, document status, approvals or page-credit usage.

Usage reports `extractionCostUsd`, `schemaSuggestionCostUsd`, successful `schemaSuggestions` and their combined `costUsd`. Successful ready suggestions use `completed_at` for the current month, so later application does not move the estimate to another month. Estimated rates verified on 13 September are USD $0.75/M input, $0.075/M cached input and $4.50/M output tokens. Failed, canceled or discarded calls may incur provider charges outside these successful-response estimates; this is not billing reconciliation. The preceding manual-suggestion checkpoint includes **14 adapter tests** and **8 hosted-worker tests**. One real suggestion completed before the first browser run stopped on an assertion. A separate **12-check follow-up** reused that recorded suggestion and completed one real extraction; it was not a single uninterrupted live-provider flow. The actual extraction matched the synthetic manifest including four line-item rows, with no issues. The final UI passed **14 grouped replay checks** using both recorded outputs and no additional live calls. `build:vercel` and isolated runtime checks for six decoders, API startup and the preview invitation guard passed; the final local suite passed **342/342 tests**, zero failures/skips/cancellations in **77.221 seconds**. ## AI-assisted first-document setup

New parser creation can explicitly choose `setupMode: sample`, `mode: ai`, and `useCase: custom`, with no supplied schema override. Both providers must be configured; API creation also requires `documents:read` alongside `parsers:write`. Preset/manual creation remains the default. Migration 025 adds persisted `awaiting_sample`, `suggesting`, `ready`, and `failed` parser states. Existing parsers default to `ready`.

The first accepted unique upload creates one `auto_setup` suggestion in the transaction that records the document, its initial extraction job and the original page reservation. Rejected uploads, duplicates and idempotent replays cannot start extra discovery. Initial jobs use `waiting_for_schema`, with a constraint requiring zero attempts, no lease, and queued/failed state. Both queue schedulers exclude these held jobs from extraction eligibility and older-work precedence. Later accepted documents wait for the same initial fields.

Successful discovery applies only while the current parser still points to that request, remains unarchived, and retains the pinned base schema. Its ready result, immutable new schema version, applied provenance, parser state, original job release and audits commit together under workspace/parser/lease checks. Held jobs receive the final schema and current parser extraction configuration without creating jobs or reprocess usage. Extracted values still enter `needs_review`; setup never approves or exports them.

`GET /api/parsers/:id/setup` returns durable state, source identity, bounded failure text, provider availability and waiting-document count. Reads require parser/document read scopes. `POST /api/parsers/:id/setup/retry` requires editor access, parser write/document read scopes and an allowed browser origin, and accepts an owned same-parser `documentId` and stable UUID `requestId`. A terminal failure marks held documents/jobs failed without attempts or further page credits; retry can choose another accepted source. Request replay returns the original operation without new capacity use. Discovery retains the shared 10-per-day/three-pending suggestion limits, bounded retries, source checksum and provider limits described above.

Saving fields manually while setup is unfinished ends automatic setup, clears its active pointer and releases held jobs with those fields. A late suggestion remains a draft and cannot replace the manual version. Deleting the active source fails remaining held work and clears only the source pointer; another accepted upload can start setup again. A new upload after another terminal failure remains visibly failed/held until explicit retry or manual save. Ordinary reprocessing is rejected until setup is ready, preserving the original upload credits for recovery.

Intake, setup transitions, manual field saves, deletion, expired-lease recovery, and worker completion/failure coordinate through a workspace advisory lock. Deletion then locks parser/document state. An extraction claim uses a nonblocking advisory attempt before changing a selected job or document and leaves busy work untouched. Provider calls occur outside database transactions. [First-document acceptance](AI-ASSISTED-SETUP-ACCEPTANCE.md) records current verification and hosted-release boundaries.

## Complete text-template selection

New intake, explicit reprocess and initial-setup release jobs pin `templatePolicy: complete-v1` alongside their schema and template snapshots. The worker evaluates those snapshots before checking AI availability or reading originals for a provider. Unstamped jobs retain the original mode-based engine and oldest-phrase template behavior. Migration 026 adds nullable, bounded `extraction_runs.selection`; old runs receive no invented decision history.

A complete template requires its literal case-sensitive document phrase (when configured), every explicit source anchor, nonmissing raw values for every configured field and required schema field, and valid normalized output. Defaults cannot establish a match. Scalar overrides cannot fall back to field labels, including CSV headers and multiline boundaries. Supported paths are scalar leaves through objects, flat scalar table columns and table headings that precede capture. Parent table rules count each child column once; overlapping parent/column rules do not double-count. Object-container anchors and nested table/object-column shapes are unsupported. More configured distinct scalar fields wins; ties use oldest creation time then ID. The run records the selected template identity, field count and tie count.

Complete matches use `text-template`, `deterministic-v3` and `folio-text-template-v1`, with no AI call, even when the AI provider is unavailable. Without a complete match, AI-mode jobs use the existing provider path. Rules-mode jobs with no enabled templates retain field-label extraction; enabled nonmatches fail permanently with an actionable explanation. Scans without native text still require AI/OCR. All successful paths remain `needs_review`; approval/export stay explicit, and checking templates adds no page credits or jobs.

The editable Templates tab and `POST /api/parsers/:id/templates/check` preview current **saved** fields/templates, mode and locale. The check requires `parsers:read` and `documents:read`, the session origin guard, and an owned same-parser source. One SQL snapshot supplies current inputs. The response contains only decision/candidate metadata, never extracted values or evidence; the check performs no writes or provider calls. UI freshness includes settings and selected document. Completed History displays the pinned run decision independently of later edits or deletion.

Template writes take the workspace advisory lock followed by the parser lock. Enabled templates validate supported anchors against the current schema; legacy invalid templates can still be disabled or deleted. Creation enforces 100 templates under that lock. Selection never chooses from a truncated candidate set; its source/rule/field/work limits and compatibility tests are recorded in [template acceptance](TEMPLATE-SELECTION-ACCEPTANCE.md). Migration 026 is local only; hosted 021–026 and matching runtime verification remain pending. This text engine does not implement OCR regions, dynamic visual anchors or managed reference-product templates.

## Parser copy

`POST /api/parsers/:id/copy` accepts strict `{name?: string}` and returns the new parser, schema, templates and export mappings. It requires an owner/admin/editor; API keys need `parsers:write`, `parsers:read` and `results:read`, with the ordinary session origin and tenant guards. A ready active or archived source produces an active destination in the same workspace. Pending/failed setup returns 409. The optional name uses the existing trimmed 1–100-character rule; the default suffix preserves valid Unicode within 100 UTF-16 code units. Names remain nonunique and the POST is non-idempotent.

The transaction takes the shared workspace advisory lock, then locks the source parser and checks the active-parser allowance. It copies use case, mode, instructions, locale, timezone and allowed formats exactly. The active schema is validated but its original JSON is persisted unchanged under a fresh schema ID at version 1; response metadata remains authoritative even if stored extensions use metadata-like keys. Setup pointers/errors, schema history and processing state are not copied. The new parser, schema, templates, mappings and one bounded `parser.copied` audit commit together or roll back together.

Templates preserve names, phrases, ordered rules and enabled flags with fresh IDs. Enabled rules validate against the copied schema; structurally valid disabled legacy rules remain disabled. The copy and selector share `compareTemplatePriority`, including JavaScript timestamp precision. A common new timestamp plus sorted fresh IDs preserves source selection priority without reusing identities or backdating copies. Only export mappings with both the source parser and workspace IDs are copied. Their structural validation preserves metadata/item paths, ordered labels, empty columns and nullable line-item expansion. Mapping collection is a one-query snapshot; existing mapping CRUD is not claimed to share every parser lock.

Copy rejects more than 100 templates, more than 100 mappings or a serialized configuration snapshot over 2 MiB, including parser settings, with 409 and no partial destination. It creates no original/storage operation, document, job, suggestion, approval, export snapshot or page usage. No email address/route, API key, OAuth state, credential or parser-specific connection is copied. Workspace-wide integrations retain their existing applicability. The UI guards duplicate submission and pending dialog dismissal; uncertain responses require checking the active parser list before retry. No new database migration is needed. [Parser-copy acceptance](PARSER-COPY-ACCEPTANCE.md) records 11 focused cases and the 394-test aggregate before a final CSS-only mobile fix, then 12 final browser groups and build/runtime checks. Exact-head CI/publication are separate; hosted 021–026 and the matching runtime release remain pending.

## Exports and integrations

CSV, XLSX and JSON exports are generated server-side from the latest approved snapshot by default; an optional document/approval selection pins a specific historical approval. Saved column mappings and nested line-item flattening apply to CSV/XLSX; JSON preserves nested values and approval/correction identity. Spreadsheet strings that could become formulas are escaped. Export snapshots persist with their input revision. Outbound webhooks use a durable delivery ledger, HMAC signatures, bounded retry, stable delivery identity and explicit replay. Destination validation rejects internal network addresses and redirects. Email intake, Google Sheets and Stripe use separate provider adapters with explicit configuration status; an unconfigured adapter cannot return success or expose a live intake address.

## Operations and acceptance

Usage events have unique idempotency keys. Quota reservations and job claiming are transactional; automatic attempts do not reserve local pages again. Provider requests may still incur retry or failed-call charges outside successful-run estimates. Explicit reprocessing is separately recorded under a documented plan rule. Retention and deletion take workspace, parser and document locks before removing database-derived copies (runs, corrections, approvals, export snapshots, webhook payloads and Sheets write reservations). The same transaction records original-file removal in the tenant-scoped `file_deletions` queue. Single-document removal normally attempts immediate storage cleanup; whole-PDF-batch removal returns its durable queue status and leaves network removal to the worker. Storage errors retain a visible pending/failed entry with bounded retries and an admin retry action. Minimal usage/audit identities remain. Existing external exports, email-provider originals, downloaded files and destination spreadsheet copies are outside this local deletion boundary. Intake event tombstones prevent a deleted document from being recreated by a repeated event; reuse of an idempotency key with different content/parser returns a conflict. Audit events retain identifiers and action metadata without document contents or credentials.

Local tests, browser verification, provider-backed extraction, live email, integration accounts, Stripe test mode, deployed revision and customer use are tracked separately in `VERIFICATION.md` and `RELEASE-GATES.md`. The initial local authorization was later extended to the invite-only preview recorded in [current hosted status](HOSTED-PREVIEW-STATUS-2026-09-13.md); it does not establish customer use or production readiness.

## Workspace capacity and membership auditing

Parser creation, copy and settings changes, including archive/restore, share a transaction-scoped workspace advisory lock. Creation, copy and only an actual archived-to-active transition check the current active count against the stored plan’s parser cap before writing through the shared capacity helper. Ordinary edits remain usable at capacity; failed restores roll back all requested changes and their audit event. ## Decoder and deployment boundary

The API now decodes original bytes in a fresh subprocess with an allowlisted environment, at most two active children per calling process, a 30-second kill deadline, 10 MiB input, 2 MiB decoded text and a 4 MiB ordinary-response limit. The compiled JavaScript child retains a 192 MiB V8 heap; TypeScript/TSX source execution receives 256 MiB for loader/compiler overhead. PDF splitting shares that capacity with its separately validated 42 MiB response bound described above. Existing page/image/Office-container bounds remain. This subprocess retains the OS user’s filesystem/network privileges; it is not an OS sandbox and does not cap native RSS or total CPU. Public untrusted uploads still require deployed OS/container identity, filesystem, network and full-resource isolation.

A durable write reservation precedes original-file creation and protects active intake. Worker maintenance reconciles old unreferenced UUID originals under workspace/row locks, using persisted filename/reservation cursors and oldest-serviced-first workspace rotation. It preserves recent, referenced and active-intake files, and eventually removes expired reservations with no file. File removal uses the durable deletion queue. Nine controlled decoder/recovery tests establish these local transitions; directory enumeration remains linear and no crash/load soak is claimed.
