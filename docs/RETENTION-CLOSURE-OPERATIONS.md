# Retention and closure: operator rehearsal

Prepared 17 October 2026 for L20/L22. This procedure and its executable local tests do not adopt a retention policy, prove hosted erasure, or create an account-closure service promise. Rory Hayes, the recorded operator, has not yet supplied the remaining provider, retention and coverage decisions in [the policy draft](LAUNCH-POLICY-DRAFTS.md).

## Request handling and stopping conditions

1. Register a minimal case reference, receipt time, requested outcome, verification result, exact user/workspace/document scope, accountable handler and evidence references. Keep original statements, passwords, tokens and raw values out of the register. Confirm whether Rory is responding as controller or assisting a customer controller. A signed-in member's role does not establish authority to erase another person's account or a shared workspace.
2. Distinguish document deletion, access removal, billing cancellation and complete account/workspace closure. Record the actual requester's instructions and third-party/other-workspace boundaries. The current supported controls cover the first three separately; they do not provide complete account erasure or a general personal-data export.
3. Inventory the applicable records before acting: originals and full source bundles, runs/revisions, local exports and deliveries, parser/integration configuration and credentials, members/sessions/API keys, usage/audit/idempotency records, account/recovery/mail/contract records, support copies, provider copies and backups. Identify any justified restriction/exception and who must decide it. Do not infer a legal hold from a foreign-key constraint.
4. Use the existing authenticated document/batch controls for an authorised deletion. A child deletion can leave its bytes inside a retained original PDF/TIFF/ZIP while siblings remain. Use the appropriate whole-batch control only when the instruction authorises the whole retained batch. Record the returned `storageDeletion` separately from the document-row outcome.
5. An owner/admin browser session can inspect `GET /api/workspace/storage-deletions` and explicitly request `POST /api/workspace/storage-deletions/:id/retry`. These are existing API controls, not an advertised Settings screen. Retry's `{ok:true}` only resets the record to pending, zero attempts and due now; it does not remove the file. Record status, attempts and the safe failure reason; verify subsequent worker completion and actual owned object absence separately. Automatic retries stop at ten failed attempts. A selected worker candidate must still be pending and due after it acquires the row lock; a concurrent stale selection cannot consume another attempt during backoff or after terminal failure.
6. If authorised, remove a non-owner member through the existing member control. It removes that workspace membership and sessions and revokes that member's workspace API keys. Verify rejection of the old session/key and preservation of separate authorised workspaces. Owner removal is blocked. This action does not remove the user's account, another workspace, immutable contract records, or prior external copies. Pause/revoke future integrations and billing only under their separately checked scope and actual provider outcome.
7. **Do not directly delete the workspace as a cleanup shortcut.** Its foreign keys cascade away `file_deletions` and `intake_files`; reconciliation also depends on an existing workspace or recorded remote intent. Losing those handles can strand physical bytes. Preserve the workspace and cleanup handles until physical removal and all retained categories are resolved in a separately reviewed closure plan. The tests' final fixture teardown is not a customer-closure implementation.
8. Respond using observed categories: completed document/access actions, pending physical removal, retained account/operational/contract categories and their still-required decisions, plus outside-copy/backup boundaries. Never report “account erased” from a successful document purge or removed membership. Actual sending, inbox verification and operator adoption remain separate.
9. Before recovering service from a backup, the backup owner must establish how adopted deletion and credential-revocation decisions are reapplied, with a protected minimal decision register. Lane05 owns backup custody, expiry, scheduling and recovery proof. No universal backup expiry or deletion-on-restore implementation is established here.

## Executable local acceptance

Use a disposable, migrated PostgreSQL database named `folio`, separate `folio_admin` and restricted `folio_app` roles, `NODE_ENV=test`, local-only database connections and a private synthetic `STORAGE_DIR`. Do not load hosted environment files. Do not run a worker alongside these global-queue tests. Local execution additionally requires the coordinator-granted runtime's `FOLIO_RETENTION_REHEARSAL_PROOF`: the guard checks the actual owned Docker container/nonce, loopback port, ephemeral PGDATA mount and cluster system identifier before fixture writes. A loopback URL alone is insufficient and host PostgreSQL is not an allowed substitute. The existing GitHub CI service has its own strict ephemeral-service path. Local tests run serially:

```sh
node --import tsx --import ./tests/test-environment.ts --test --test-concurrency=1 tests/file-deletion-claim.test.ts tests/retention-closure-rehearsal.test.ts tests/retention-notifications.test.ts tests/defensive-regressions.test.ts
```

- `file-deletion-claim.test.ts`: two workers select the same due removal while the first holds the real PostgreSQL row lock; after its failure, the second must preserve both new backoff and terminal failure. Reserved-byte intent and synthetic bytes remain until explicit recovery. The parent code must fail the exactly-one-removal assertion.
- `retention-closure-rehearsal.test.ts`: an authenticated owner request and denied foreign/viewer requests; pending and terminal storage failure with authorised recovery; document-age expiry and an aged orphan alongside fresh, leased, active and foreign controls; old session/key rejection after access removal while account/other-workspace rows and bytes remain exact. Ageing is deliberate fixture timestamp setup, not an elapsed hosted retention period.
- Existing retention/defensive regressions retain the deeper local derived-record deletion, usage/audit/tombstone preservation and no-resurrection checks. These tests do not verify provider versions, backups, consumer inbox handling or full account closure.
