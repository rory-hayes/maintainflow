# OpenDocument text intake

This is a bounded addition to the existing MaintainFlow source registry and C09 criterion. It does not complete all OpenDocument or additional-format support. ODS, ODP, legacy Office, presentations and the other open converters remain outside this increment. The original 47 capability criteria and the bank-statement workflow remain in scope.

## Supported contract

- Unencrypted ODT packages explicitly declaring OpenDocument 1.2 or 1.3, with matching package MIME, manifest and content version. Classification uses ZIP metadata; full package validation and XML decoding run inside the existing isolated document decoder.
- UTF-8 XML 1.0; body paragraphs, headings, inline spans/links, explicit spaces/tabs/line breaks, simple sections and rectangular tables. Supported list numbering requires an explicit source label or a supported declared decimal/bullet style. The converter never follows links or retrieves remote resources.
- Paragraphs remain separate. Tables become tab-separated text, retaining empty columns, literal pipes, leading zeros and displayed strings. Paragraph/line breaks inside a table cell become spaces. Value/formula metadata never supplies an absent displayed value.
- One logical extraction page, as with existing DOCX text extraction. Physical pages, layout, image OCR and coordinate evidence are not manufactured. The review pane identifies the ODT text preview and keeps the unchanged original downloadable.
- Existing 10 MiB file and 20-file batch limits apply, with any smaller workspace allowance. The decoder additionally limits packages to 2,000 ZIP records, 40 MiB actual aggregate expansion, 10 MiB per member, XML depth 64, 100,000 XML nodes, 20,000 paragraphs, 10,000 emitted table rows, 100,000 emitted cells, 1,000 columns/repetitions and 2 MiB projected text. Existing child deadline and memory limits remain.
- ODT inside a selected ZIP import is one atomic document. Office leaves share the existing 40 MiB expansion allowance. Importing an ODT package as an archive is refused; its internal XML files do not become separate documents.

## Visible refusals and limitations

Encrypted files, DTD/entity declarations, XML processing instructions, malformed/unsafe packages, unsupported versions and unsupported body structures fail visibly. Embedded objects/images, annotations/notes, tracked changes, forms, headers/footers, hidden/conditional content, unresolved/complex/continued list numbering, merged/nested/ragged tables and table-cell tabs are not projected. Rich documents may therefore need an unencrypted text-based PDF or DOCX export. This is not universal ODT compatibility or a page-layout renderer.

A matching filename is insufficient. Renamed ODT is still subject to the ODT policy after child validation; malformed files do not create partial jobs or page charges. Raw source text and extracted values remain available alongside normalized values and corrections. Existing saved normalization settings, explicit approvals and immutable export revisions are reused. No separate authentication, storage, permissions, billing or processing system was introduced.

## Verification and release

Synthetic fixtures are independently authored packages, including the reproducible `fixtures/source-formats/synthetic-receipt.odt` generated by `scripts/fixtures-odt.mjs`. They contain no real customer or bank data. Unit tests cover text/namespace/whitespace/table fidelity and adversarial package, XML, repetition and expansion limits. API tests exercise real intake, jobs, parser policies, permissions, corrections, approval history, exact CSV/XLSX/JSON, signed-upload retries/tombstones and selected ZIP imports with controlled provider transport only.

The deployable-bundle check decodes the fixture through the compiled child and verifies an atomic ZIP leaf. The encrypted filesystem recovery drill retains an ODT original and resumes its queued job once with its pinned normalization settings and unchanged usage.

Migration **042** extends existing parser and durable receipt constraints; it creates no tables or grants. It preserves the latest PDF/TIFF split contract. Runtime readiness requires all five validated format/receipt constraints to admit the new format and rejection reasons. That is a release capability check, not an arbitrary SQL-constraint equivalence proof. Apply and verify migrations in order before activating matching runtime. Existing approved/pending 039–040 and 041 payloads must not be broadened implicitly. Once ODT work has been admitted, older runtimes cannot decode its queued jobs. A rollback therefore needs an intake pause and explicit queue handling or a forward fix; the original files and approved snapshots remain retained.

Current local verification and draft/deployment status are recorded in the task's release evidence. No hosted database change, real provider request, broad bank compatibility, measured extraction accuracy or customer-use evidence is implied by these fixtures. Free plans and mock billing remain unchanged.

## Format references

The implementation follows the bounded subset above of the [OASIS OpenDocument 1.3 package specification](https://docs.oasis-open.org/office/OpenDocument/v1.3/os/part2-packages/OpenDocument-v1.3-os-part2-packages.html), using the [saxes XML parser](https://github.com/lddubeau/saxes) with DTDs and processing instructions refused.
