# Empty legacy installation upgrade

This separate, one-time support path upgrades only the explicitly approved
Supabase project `dhbevbimoajwkuzcunwz` from the exact recorded migrations
001–018 to the exact reviewed 001–027 release. It preserves the existing schema
and applies only 019–027. It is not a general migration override.

The normal [hosted migration runner](database-migrations.md) and the
[pristine bootstrap](empty-hosted-database-bootstrap.md) retain their existing
guards. Neither accepts this workflow's local recovery evidence as a hosted
backup or restore rehearsal. A database containing customer state must use the
normal backup/restore workflow.

## Required evidence

1. Confirm the selected SQL editor belongs to `dhbevbimoajwkuzcunwz` and the
   owner has authorized replacing that unused installation. SQL alone cannot
   infer a Supabase project reference from the common database name `postgres`.
2. Run the read-only `scripts/empty-legacy-catalog.sql` query and save its exact
   JSON result privately. Capture the full public application structure,
   constraints, indexes, policies, triggers, database and object privileges,
   role attributes and memberships, and the pinned provider RLS helper. Do not export passwords,
   tokens, credential hashes or customer records.
3. Wrap the result in a mode-0600 baseline JSON file containing
   `kind: maintainflow.empty_legacy_baseline`, `version: 1`, the exact
   `projectRef`, an ISO `capturedAt`, and `catalog: <query result>`.
4. Reconstruct the known empty application baseline in owned, isolated local
   PostgreSQL 17 using the immutable 001–018 files and the explicitly captured
   application role/ACL configuration. Compare its structure to the live
   capture. Supabase platform roles and provider-owned objects are captured
   boundaries, not objects generated by the application migrations.
5. Export that reconstructed empty schema and application role configuration,
   restore it into a second fresh owned local target, and verify schema,
   grants, role flags and empty application state match. Preserve passing
   evidence bound to the exact captured baseline and full migration manifest.
   Merely replaying migrations or saving catalog JSON is not a restore drill.
6. Exercise the generated transaction on disposable PostgreSQL: success;
   retained application/Auth/Storage state; ledger, schema, helper and ACL
   drift; unsafe role/session state; and an injected mid-migration failure.
   Failures must leave all schema, ledger and role changes rolled back.

A narrow supplemental read-only export may supply an omitted catalog field
only from actual captured metadata. Preserve both raw exports, their hashes
and capture times; use the earliest capture time for evidence freshness. The
full combined snapshot must still match the current query inside the guarded
transaction. Do not infer unobserved grants or omit unexplained differences.

This proves local reconstruction and recovery of a known empty application
schema. It does not prove hosted backup availability, provider disaster
recovery, Auth continuity, or recovery of existing connection credentials.

The recovery evidence uses `kind: maintainflow.empty_legacy_local_recovery`,
`version: 1`, the exact `projectRef`, `baselineSha256` (SHA-256 of canonical
baseline JSON), `migrationManifestSha256`, ISO `completedAt`, and four passing
`checks`: `canonicalPrefixMatches`, `localSchemaRestoreMatches`,
`localRoleAclRestoreMatches`, and `emptyState`. Seal the manifest with the
existing `withManifestChecksum` helper. The generator requires both capture
and recovery evidence to be no more than 24 hours old, rejects future dates,
and requires recovery to follow capture.

## Generate and review

The repeatable synthetic integration check uses two private PostgreSQL 17
clusters over owned Unix sockets and removes them afterward:

```sh
PG_BIN=/path/to/postgresql17/bin node scripts/verify-empty-legacy-bootstrap.mjs /private/evidence/empty-legacy-integration.json
```

This check exercises guards, late-failure rollback and the actual runtime
verifier. Its synthetic fixture does not replace recovery of the separately
captured live application schema and role/ACL profile described above.

After review and commit, use the exact clean release checkout:

```sh
node scripts/generate-empty-legacy-bootstrap.mjs \
  --baseline /private/evidence/empty-legacy-baseline.json \
  --recovery-evidence /private/evidence/empty-legacy-local-recovery.json \
  --output /private/evidence/empty-legacy-upgrade.sql \
  --expected-build-sha <full-reviewed-git-sha>
```

The output must be a new mode-0600 file outside the checkout. Review its target,
source SHA, evidence hashes, guards, immutable migration segments and role
retirement. Immediately before the authorized SQL editor execution, verify
the selected project and hash the editor contents against the reviewed file.
Record the provider execution reference, UTC time, artifact SHA and read-back
verification. Do not execute a differently edited SQL selection.

## Transaction boundary

The artifact takes the normal migration advisory lock, sets `row_security=off`
and bounded timeouts, then locks all 15 existing application tables, the
ledger, `auth.users`, `auth.identities`, `auth.sessions`, `storage.buckets` and
`storage.objects`. Every retained-state table must still be empty. Missing
provider tables, lock contention, RLS restrictions, unknown objects, changed
catalog/ACL metadata, a different ledger, an existing new runtime role, or an
old runtime session cause refusal. The exact official RLS helper is preserved. Migration 027 explicitly permits the
server runtime to resolve public site IDs while requiring the correct workspace
context for site inserts, updates and deletes; it fixes the otherwise denied
registry writes when the provider helper enables RLS.

All nine migration bodies and their ledger entries execute in one
transaction. In the same transaction, the obsolete `maintainflow_app` becomes
`NOLOGIN NOBYPASSRLS NOINHERIT` and loses public table, explicit column,
sequence, function and schema access, plus its direct database grants.
This is necessary because immutable migration 023 grants that legacy role
access to new attribution tables. The transaction checks the complete
27-entry ledger, 24 application-schema tables, continued empty state and the
final role boundary before commit. No provider objects are dropped and no
password is generated, copied or changed.

The new `maintaincode_app` remains `NOLOGIN NOBYPASSRLS`. Provision its separate
server-only runtime credential through the approved secret manager afterward,
then run the normal read-only hosted runtime/RLS verifier before switching
application traffic. A migration success alone is not a production cutover.

If any guard fails, stop and preserve the error and fresh inventory. Do not
remove tables, alter the ledger, normalize unexplained catalog differences,
disable guards, relabel local evidence as hosted recovery, or retry against
another project. Resolve the actual discrepancy or use the normal hosted
backup/restore process with an approved distinct restore destination.
