## Read-only preflight

`scripts/launch-preflight.ts` checks a strict private pre-activation manifest, explicit SHA256-pinned evidence, independent target pins and clean local `main`. It imports no application configuration, loads no `.env`, makes no network/provider calls and writes nothing. It does not infer completion from another lane's `STATUS.json`, a successful build or a count of local tests. A complete manifest still returns `productionReady:false`, `activationAuthorized:false` and `activationPerformed:false`.

Create a template in a new private evidence packet, then have the coordinator fill it from accepted evidence. Use the installed Node 24 executable or an equivalent centrally verified Node 24 runtime. Run repository commands from the integration checkout only when the coordinator performs this handoff:

```sh
node --import tsx scripts/launch-preflight.ts --template > /absolute/private/new-packet/manifest.json
git rev-parse HEAD
git rev-parse 'HEAD^{tree}'
node --import tsx scripts/launch-preflight.ts --manifest /absolute/private/new-packet/manifest.json --expected-commit FULL_MERGED_COMMIT --expected-tree FULL_TESTED_TREE > /absolute/private/new-packet/preflight.json
```

The independently reviewed intended merge/tree belong in the command. Do not copy arbitrary target values from an unreviewed manifest. Exit 0 means evidence is structurally complete for coordinator review; exit 1 means an unmet gate; exit 2 means invalid arguments, unreadable input or an invalid checkout. An action flag such as `--activate` is refused. The template command's exit 0 means only that a template was printed.

Each named acceptance needs `status:accepted`, the permitted evidence tier, no unresolved requirement, a nonempty reviewer, review time within seven days, the exact final `reviewedAgainstTree`, and a pinned actual receipt. Keep original test/source revisions, limitations and failures inside that receipt. A coordinator may review older demonstrated behavior against the final tree only with an explicit compatibility/revalidation assessment; changing its label does not rerun it. The script checks assertions and file integrity, not the authenticity or semantic sufficiency of their producers. The coordinator must read and accept the underlying evidence.

Allowed evidence tiers are `hosted` (actual application/provider boundary), `stripe_sandbox` (real Stripe TEST lifecycle), `provider_readback` (actual account/catalog/permission/cost readback) and `operator_adoption` (factual, adopted operating choices). `local_fixture` and `source_only` never close a hosted/provider acceptance. Files must be explicit absolute paths to bounded evidence files (`.json`, `.md`, `.txt`, `.log`), not environment or credential files. Do not include keys, reusable URLs, headers, cookies, card details or customer content.

## Containment and rollback

The manifest's `rollback` pins a distinct previous commit/tree, immutable deployment ID/host, explicit schema compatibility and SHA256-pinned JSON receipt. The receipt must contain `status:verified`, those four identities, `schemaCompatible:true`, `evidenceTier:hosted`, `isolatedRoutingRehearsal:true`, `sourceDataUnchanged:true`, `outboundFenced:true`, a nonempty `reviewedBy` and `verifiedAtUTC` within 24 hours. The lane's prepared checklist is not this rehearsal.

| Trigger | Coordinator action and required evidence |
| --- | --- |
| Wrong source/domain/WAF, signup bypass, tenant/privacy violation, unexplained live charge, data corruption or uncontrolled duplicate processing | Stop the activation acceptance and new intake using the reviewed reversible containment. Preserve diagnostics, queue/usage/provider identities and timestamps. Keep monitor/incident evidence; do not disable monitors or clear failures to obtain green status. |
| Failed/uncertain provider mutation or timeout | Inspect the exact reserved action's actual outcome first. Preserve failed and uncertain receipts. Never blindly retry a domain/WAF/payment action or restart a process whose handle is still live. |
| Routing rollback is compatible | Re-read the known-good immutable deployment, current alias and full WAF baseline. Coordinator stages the inverse one-host replacement and reviewed canonical routing target; obtain the same independent exact-draft review, then publish and verify full WAF/no draft. Preserve authentication/private invite/mock containment and all unrelated rules. Do not add wildcard hosts or leave both retired deployment hosts allowed. |
| Current database schema/data is incompatible with the older app | Keep public intake contained and use the reviewed forward fix or verified isolated recovery plan. Do not run down migrations, drop data, overwrite current provider history or restore over the canonical database as an automatic rollback. Reconcile new writes and payment events first. |
| After rollback | Capture exact old runtime revision, readiness, signup denial/private configuration, original/export retrieval, queue/accounting isolation, integrations, monitoring and full canonical/WAF receipts. Keep live subscriptions/events and customer obligations accounted for; switching the UI back to mock is not a cancellation/refund or entitlement reconciliation. Retire temporary routes/resources only after actual outcomes are known. |

No generic provider rollback executor is supplied: a reusable command cannot safely choose the current aliases, WAF version, provider state or database compatibility. The reviewed packet supplies the concrete current-state actions for the sole coordinator.
