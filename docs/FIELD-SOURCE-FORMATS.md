# Source formats for individual fields

This extension implements the missing per-field format control in W06 and tightens R02 number admission for new general-document extractions. It reuses saved parser schemas, job settings, immutable extraction runs, corrections, approvals and exports. The bank-statement workflow continues to use its existing per-upload format and exact monetary calculations.

## Using the control

Open a parser's **Fields** tab, expand **Extraction options** for a date, number, currency or timestamp field, then choose **Source format**. **Use parser format** uses the parser locale saved with that extraction. An explicit choice applies only to that field, including a scalar inside an object or table. Changing the field to text or another ineligible type clears the override.

Available overrides are Ireland (`en-IE`), United Kingdom (`en-GB`), United States (`en-US`), Germany (`de-DE`), France (`fr-FR`) and Spain (`es-ES`). These describe source date order, written-month language and number punctuation. They do not choose a timezone. For example, one Irish parser can read `04/05/2026` as 5 April in a US field and 4 May in a field using its Irish default, while a German amount `1.234,56` becomes `1234.56`.

New extraction validates the complete number, including grouping positions, decimal punctuation, signs and currency markers. An Irish number `12,34` or `1.234,56` remains unresolved with a validation issue. An unresolved required or invalid value cannot be approved merely because extraction completed. The original value and available source evidence remain available for comparison. Saving corrections refreshes current validation warnings; immutable extraction issues remain in the original run record. Supported grouping is determined by the saved locale; French grouping accepts ordinary, nonbreaking or narrow nonbreaking spaces, without guessing a mixed separator convention.

Review corrections are canonical values: numeric corrections use a decimal point without thousands separators, and date corrections use the calendar date control. A corrected `1234.56` is never reinterpreted as German source punctuation. Timestamp corrections use the immutable field format and saved run timezone, while an explicit offset identifies the instant directly. Repeated or nonexistent local clock times still need review. Defaults keep their existing explicit canonical-value contract; source punctuation is not reapplied to numeric/date defaults.

## Version and release contract

New general-parser jobs pin `regional-v2`. The worker forwards that policy through deterministic rules, text templates, native-PDF regions and the configured extraction provider. Preview uses the current policy. Each result records its actual policy, locale, timezone and timezone database version. Schema edits create a new immutable version; parser copies preserve field overrides but have independent identities.

Jobs already queued with `timestamp-v1`, or with no saved policy, retain the legacy interpretation. This includes jobs waiting for initial schema setup. If an old waiting job is assigned new field overrides, it fails visibly with a reprocess instruction instead of silently ignoring those overrides. Missing historical run context does not borrow the current parser's settings. Stored raw/normalized values, corrections, approvals and export snapshots are not rewritten. Explicit reprocessing of a general document creates a new job using current saved settings and the current policy. Unsupported future policies fail before extraction rather than guessing.

Compatibility therefore preserves a known limitation for old queued jobs: the old permissive number parser can accept malformed grouping. Inspect those results carefully or explicitly reprocess to use the stricter policy. This limitation is not retained for new general extraction jobs.

Migration **041** broadens the existing run-context version constraint to accept the two known versions. It retains the existing four-key shape, nullable historical context, value checks and denial of unknown versions/extra keys. It does not rewrite saved results or grant new table access. Apply it before deploying the matching application runtime, following the existing release process. The readiness probe must also recognize the supported constraint before reporting the database ready. This release remains separate from pending bank migrations 039/040 and their access approval. Once new field overrides or `regional-v2` jobs/results exist, a pre-feature application rollback is not a complete compatibility strategy: older correction handlers do not understand field formats, and older workers may reject the new policy. Stop affected writes and job processing before a coordinated rollback; preserve their snapshots and prefer a verified forward fix. Do not reinterpret those jobs or results under the old policy.

## Evidence and limits

Local verification on 26 September 2026 passed 226 focused tests, TypeScript and web builds, the packaged function runtime/decoder check, and the isolated managed-backup restore drill. The focused suite covers strict regional interpretation, provider-adapter transport, both template generations, queue/schema version boundaries, corrections, approval/export history, permissions, workspace isolation and existing bank regressions. Its application/test fingerprint is retained; a subsequent frontend-only table-hint wrapping fix was checked in a fresh build and browser run.

Nine browser check groups passed with a clearly labelled synthetic native PDF at 1440 × 1000 and 390 × 844. They exercise actual sign-in, schema save/reload, upload, original-byte identity and source evidence, unresolved-value approval refusal, saved corrections, mobile approval, actual JSON/CSV/XLSX downloads and exact cells, historical approval retention after reprocessing, read-only controls, and page/console/network checks. Screenshots were inspected; source-format table hints wrap within bounded columns. The walkthrough respects the existing request-rate window. No external provider calls were made. Full repository CI is tracked separately on the draft pull request; these local checks do not claim hosted migration/deployment acceptance or real-provider accuracy.

These controls do not establish universal language, banking or OCR compatibility. Existing document/row/export limits and workspace quotas apply. General numeric fields retain their existing finite JavaScript-number domain; this change does not add arbitrary-precision accounting. Bank-statement monetary amounts use their separate decimal-safe domain. Free provider plans and mocked billing remain unchanged.
